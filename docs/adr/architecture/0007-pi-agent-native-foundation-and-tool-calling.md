# 架构 ADR 0007：全面拥抱 Pi Agent 底座与原生 Tool Calling 标准（拒绝自研轮子）

- 状态：已采纳（现行系统基石，继承 0018）
- 领域：大语言模型（LLM）通信内核 / 智能体（Agent）底层架构

## 背景

在项目早期，系统曾尝试自研 Agent 引擎与通信解析器：
1. 采用非结构化文本输出，要求模型输出包含特定 XML/JSON/DSML 标记；
2. 应用层手工编写复杂的正则表达式（`parseToolCalls`）从返回文本中剥离工具调用并拼装假消息回灌；
3. 自研事件循环与状态机驱动 ReAct 决策。

这套自研机制在长篇小说复杂场景下彻底崩溃：一旦上下文长达数万字或大模型输出带有思维链（Thinking），模型经常丢失转义引号、破坏 XML 结构，导致应用频繁出现死循环或解析崩溃。同时，针对不同厂商（OpenAI、Gemini、Claude、DeepSeek、Ollama 等）的协议差异，应用层不得不维护数十个专有补丁。

## 决策

**彻底废除所有自研的文本工具协议、正则提取器与自制 ReAct 循环，100% 拥抱并深度复用 `@earendil-works/pi-agent-core` 与 `@earendil-works/pi-ai` 作为底层基石。**

1. **坚持最大化复用原则，严禁盲目自研**：
   * **通信层**：直接复用 `@earendil-works/pi-ai`，由其适配器统一抹平全球主流模型提供商（OpenAI 兼容协议、Google Gemini、Anthropic 等）的底层协议差异；
   * **函数调用标准化**：正文生成与数据提取全面收归各模型原生的 Function Calling，入参由 TypeBox 生成的 JSON Schema 强类型约束；
   * **单发与多轮复用**：工作流生成（如批量起草、大纲提取）与边栏多轮对话助手共用同一套底层适配底座。
2. **密钥与通信彻底收归主进程**：
   * API Key、网络代理端点与模型连接统一在 Electron 主进程中执行，渲染进程不直接发起大模型 HTTP 通信，保障端点安全。
3. **能力门控与结构化强制**：
   * 参与正文起草与领域操作的模型必须支持工具调用（`toolCalling`）；
   * 工作流生成通过强制 `submit_*` 工具作为唯一合法交卷出口，彻底消除了非结构化文本的格式崩坏。

## 后果与权衡

* **收益**：删除了上千行脆弱的自研通信与解析死码，模型调用稳定性和跨厂商兼容性获得质的飞跃；
* **代价**：对于极少数完全不支持原生 Function Calling 的古董小模型，系统明确拒绝其作为生成主力模型使用。
