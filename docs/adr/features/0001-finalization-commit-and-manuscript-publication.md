# 功能 ADR 0001：定稿正文不可变提交与实体稿物理发布

- 状态：已采纳（现行业务规则）
- 领域：小说正文生命周期 / 定稿与发布系统

## 背景

长篇小说在写作过程中存在“正在起草修改的草稿”与“已经完成推敲、不可随意篡改的正式定稿”之分。如果将定稿直接存储为普通可编辑文本文件，极易遭受误编辑、意外覆盖，导致后文依赖的前文情节事实崩塌。

## 决策

**定稿必须以编辑器提交的不可变快照为输入，SQLite 数据库中的定稿内容是权威事实源，磁盘上的实体文件是可恢复的发布投影。**

1. **事实源与发布投影分层**：
   * SQLite 中的 `finalized_chapters` 表持有不可变定稿正文事实；
   * 磁盘根目录下的章节 Markdown 文件（如 `第一章.md`）是由发布器原子落盘生成的只读实体稿投影；
2. **两阶段安全提交**：
   * 一次定稿在数据库事务中冻结正文快照、计算内容哈希并记录发布任务；随后由实体稿发布器执行原子物理落盘；
   * 若磁盘写入失败，系统标记为“定稿已提交、实体稿待发布”，可安全幂等重试；
3. **编辑冲突保护**：
   * 定稿提交后，若作者在编辑器中继续产生了本地编辑，系统严禁就地静默覆盖，而是保留本地改动并显式提示作者进入分叉或冲突确认状态。

## 后果与权衡

* **收益**：彻底保障了小说已发布定稿的确定性与不可篡改性，为后续连续性审查提供了坚实的基准；
* **代价**：定稿章节的再次修改需要显式走“解除定稿”或“生成修订候选”流程，不能直接盲目涂改。
